Two changes to the analysis below, made after independently re-running the audits with

**2. Root entries marked `accepted` below were upgradable after all.**

The reachability reasoning in those rows still stands — a Next.js static export has no

exposure. What was wrong is the conclusion that no fix existed short of a major bump.

Build-host exposure is still exposure: it is where credentials and signing material live.
An advisory that can be closed by a lockfile-only bump should be closed, not accepted with
a review date.

The two remaining highs (`next`, `postcss`) do require `next@16`, a major. Those stay
`blocked` pending a ticket with real integration testing, as the constraint intended.

Verified after the change: `npm ci` clean, `npm run test:unit` 62/62, `npx tsc --noEmit`
clean, `npm --prefix functions run build` exit 0, and the 16 deterministic production E2E
specs still green.

## Decision summary

The tracked audit evidence records 23 root entries (2 critical, 8 high, 12 moderate, 1 low) and 22 Functions entries (2 critical, 5 high, 13 moderate, 2 low). These are package-level npm audit entries, not counts of confirmed exploitable application paths. The root app is a Next.js 14 static export (`next.config.js` sets `output: 'export'`) deployed as Firebase Hosting files; it has no deployed Next server, SSR runtime, middleware runtime, or Next image optimizer. Functions are Node 22 Cloud Functions v2 and are server-side.

The Functions lockfile received only compatible minor/patch updates. The manifests remain compatible with both lockfiles. No application dependency was removed: source imports were checked with `rg` for every direct package and the transitive packages below are not imported by application source.

Safe upgrades applied in `functions/package-lock.json` include `firebase-admin` 13.7.0 → 13.10.0, `@grpc/grpc-js` 1.14.3 → 1.14.4, `protobufjs` 7.5.4 → 7.6.6, `fast-xml-parser` 5.5.8 → 5.11.1, `fast-xml-builder` 1.1.4 → 1.3.1, `form-data` 2.5.5 → 2.5.6, `node-forge` 1.3.3 → removed by the compatible Admin update, `path-to-regexp` 0.1.12 → 0.1.13, `body-parser` 1.20.4 → 1.20.6, `qs` 6.14.2 → 6.15.3, `@tootallnate/once` 2.0.0 → 2.0.1, and `websocket-driver` 0.7.4 → 0.7.5. The remaining Functions entries are deliberately blocked or accepted below.

Evidence: [root audit evidence](./evidence/web-dependency-audit.json), [Functions audit evidence](./evidence/functions-dependency-audit.json), [root manifest](../../../package.json), [Functions manifest](../../../functions/package.json), [root lockfile](../../../package-lock.json), [Functions lockfile](../../../functions/package-lock.json).

Comparing the post-change lockfile to those exact baseline ranges gives root **23** (2 critical, 8 high, 12 moderate, 1 low) and Functions **11** (0 critical, 0 high, 11 moderate, 0 low). The Functions audit could not query the registry after the lockfile install attempt (`getaddrinfo ENOTFOUND registry.npmjs.org`); its post-change count above is the lockfile comparison against the tracked baseline ranges and must be confirmed with registry access before merge.

Root `npm ci` exited 0. Functions `npm ci` could not complete because the sandbox has no cached `googleapis@148.0.0` tarball and registry DNS is unavailable; this is an environment verification blocker, not a lockfile consistency error. Re-run Functions `npm ci`, the Functions build, and the Functions audit with registry access before merge.

Commands run for reachability evidence included `npm explain` for each affected package, `rg` source-import checks, and inspection of `next.config.js`, `functions/src`, and both lockfiles. `npm ci`, unit tests, TypeScript checking, and the Functions build are the release checks for this change; deployment and major upgrades remain out of scope.
